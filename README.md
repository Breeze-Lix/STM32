# FreeRTOS_and_PID

> 本工程关于学习 FreeRTOS 的内容，同时进行 PID 的学习

## FreeRTOS 概念

### 是什么

FreeRTOS 是跑在单片机上的**调度器**，负责决定"此刻该哪个任务占用 CPU"。

单核 CPU **不可能真正并行**，它做的是快速切换：一个任务跑到阻塞点（`osDelay`、等队列）就换下一个，切得够快，看起来像同时。

### 三个核心概念

| 概念 | 含义 |
|---|---|
| **Task（任务）** | 一个独立的 `for(;;)` 函数，有自己的栈和优先级 |
| **Tick（节拍）** | 系统心跳，默认 1ms 一次；`osDelay(100)` 就是等 100 个 tick |
| **Priority（优先级）** | 数字越大越优先；高优先级不阻塞时，低优先级永远轮不到 |

### 和裸机 `while(1)` 的区别

| | 裸机 | FreeRTOS |
|---|---|---|
| 代码组织 | 所有事挤在一个循环 | 每件事一个任务，各写各的 |
| 某处卡住 | **全部停摆** | 只影响自己 |
| 加新功能 | 改整个循环 | 新建一个任务 |

### 两个必须记住的细节

**① 启用 RTOS 后 `main()` 的 `while(1)` 变成死代码**

`osKernelStart()` 不返回，CPU 交给调度器之后再也回不来。所有业务都要写进任务函数。

**② `osDelay` 和 `HAL_Delay` 完全不同**

| | 行为 |
|---|---|
| `HAL_Delay(100)` | CPU 死等 100ms，什么都干不了 |
| `osDelay(100)` | 主动交出 CPU，调度器去跑别的任务 |

### 三个踩过的坑

| 坑 | 现象 | 原因 |
|---|---|---|
| Timebase 没改成 TIM3 | 卡在 `printf`、LED 不闪 | FreeRTOS 和 HAL 抢 SysTick |
| 堆太小（3072） | 第二个任务创建不出来，且不报错 | `osThreadCreate` 返回 NULL |
| 栈太小（128） | 跑几秒 HardFault | `printf` 一个人就要 1KB |

### 任务间怎么传值

| 方式 | 语义 | 适合 |
|---|---|---|
| `volatile` 全局变量 | 最新值覆盖 | 目标速度、目标角度（旧值没意义） |
| 队列 | 每条都排队、不丢 | 指令、数据包（每条都要处理） |

判断依据：**旧值还有用吗？** 没用就用全局变量，有用就用队列。

## 1. 新建 FreeRTOS 工程

**CubeMX 配置：**

1. 在 `Middleware and Software Packs` 里面找 FreeRTOS
2. 设置 `Interface` → **CMSIS_V1**
3. 设置 `Stack Size` → **256**
4. 在 `System Core` 里面找 SYS，设置 `Timebase Source` → **TIM3**
5. 生成代码，用板载灯闪灯检验，位置 `void StartDefaultTask` → `for` 循环

> **注**：记得开启 USART2（**不用配 DMA / NVIC**）并加入 `fputc` 重定向 + 勾选 **Use MicroLIB**，否则 `printf` 会卡死。

## 2. 任务并行

**① 加第二个任务**

`FreeRTOS → Tasks and Queues → Tasks → Add`：

| 参数 | 填写 |
|---|---|
| Task Name | `sinTask` |
| Priority | `osPriorityNormal` |
| Stack Size | `256` |
| Entry Function | `StartSinTask` |

**② 两个任务用不同周期，先验证调度**

`defaultTask` 打印 `A`、延时 100ms；`sinTask` 打印 `B`、延时 500ms。

预期输出（每 5 个 A 出现 1 个 B）：

```text
A A A A A B A A A A A B ...
```

**③ 改成生产者 / 消费者**

`sinTask` 每 10ms 算一次正弦目标值写入 `g_target`，`defaultTask` 每 100ms 打印一次：

```text
target=0.0
target=30.9
target=58.8
target=80.9
target=95.1
target=95.1
target=80.9
...
```

> **注**：`g_target` 被两个任务读写，**必须加 `volatile`**。
> 生产快（100Hz）、消费慢（10Hz），和真实 PID 场景一致。

## 3. PID 算法

### 3.1 PID 在干什么

根据误差，算出该给多大的输出。

目标值减去实际值得到误差，误差送进 PID，PID 算出输出驱动执行器，执行器产生新的实际值，再反馈回来——这就是一个闭环。

### 3.2 三项各管什么

| 项 | 看的是什么 | 作用 | 调太大 | 调太小 |
|---|---|---|---|---|
| P（比例） | 当前误差 | 误差越大出力越大，管"反应快" | 振荡、超调 | 反应慢、有静差 |
| I（积分） | 历史误差累加 | 消除静差，管"最终能到位" | 超调、积分饱和 | 永远差一点到不了 |
| D（微分） | 误差的变化率 | 预判趋势、提前刹车 | 对噪声极敏感、抖动 | 超调大、震荡 |

> **"静差"是什么**：只用 P 的时候，要维持一个输出就必须保留一点误差。
> 比如目标 100，实际稳定在 95，那 5 就是静差——P 越大静差越小，但永远消不掉。
> 这就是为什么需要 I。

### 3.3 用的是位置式 PID

```text
u[k] = Kp·e[k] + Ki·Σ(e·dt) + Kd·(e[k] - e[k-1])/dt
       ↑           ↑                    ↑
     当前误差    历史累加             误差变化

直接把 u[k] 送给执行器
```

**为什么选位置式**：PWM 占空比本身就是个绝对量，算出来直接送给执行器就行，不需要"在上一刻基础上加多少"那种增量语义。

> 增量式算的是 `Δu`，还要自己维护 `u[k-1]` 累加。
> 它天然没有积分饱和问题，但更适合步进电机这类"靠脉冲累加"的执行器。

### 3.4 代码和公式的对应

```c
p->integral += err * dt;                  /* Σ(e·dt)：历史误差累加 */
deriv = (err - p->err_prev) / dt;         /* de/dt：误差变化率 */
out = kp*err + ki*p->integral + kd*deriv; /* 三项相加 */
```

| 公式里的项 | 代码里的变量 | 含义 |
|---|---|---|
| `e[k]` | `err` | 当前误差 = 目标 − 实际 |
| `Σ(e·dt)` | `p->integral` | 历史误差的累加 |
| `de/dt` | `deriv` | 误差变化率 |

**为什么 `integral` 要存在结构体里**：它是跨调用累加的。写成函数内的局部变量，每次调用都归零，I 项就废了。

### 3.5 仿真电机

`Motor_GetSpeed()` 里的三行就是一个"假电机"：

```c
const float T = 0.1f;                       /* 时间常数：越大越"肉" */
const float K = 3.0f;                       /* 100% 输出 → 300 rpm */
float target = s_out * K;
s_speed += (target - s_speed) * 0.01f / T;  /* 每步只朝目标走 10% */
```

**最后那一行就是"惯性"的数学表达**：转速不会瞬间到位，而是每 10ms 朝目标挪一点。

接真电机后，这段换成"读编码器 + 写 PWM"，**PID 和任务的代码一行都不用改**。

> **已知近似**：仿真假设调用周期严格等于 10ms。实际 `osDelay(10)` 会有几毫秒抖动，
> 所以仿真的"时间"比真实时间略慢。对观察曲线形状没有影响。

### 3.6 调参顺序

**一次只动一个参数**，每次看阶跃响应（把 `g_target` 固定成常数）。

1. **只留 P**（`ki=kd=0`），从 1 开始加，加到响应够快但还没明显振荡
2. **加 I**，从小往大，消除静差
3. **加 D**，从小往大，压超调

| 曲线现象 | 该怎么调 |
|---|---|
| 爬得很慢 | P 太小 |
| 冲到 130 再回落 | P 太大，或 I 太猛 |
| 稳定在 95 上不去 | I 太小，或 `int_max` 太小 |
| 上下振荡不停 | P 太大，或 D 太小 |

> **`int_max` 不是随便填的**：至少要 `out_max / ki`。
> 比如 `out_max = 100, ki = 0.5`，积分要能单独撑起满输出，就需要 `int_max ≥ 200`。

### 3.7 实现时的三道保险

| 保险 | 不做会怎样 | 原因 |
|---|---|---|
| **首帧微分置零** | 上电瞬间输出猛抖一下 | `err_prev` 初值 0，`(err - 0)/dt` 产生巨大冲击 |
| **积分限幅** | 退饱和慢、严重超调 | 输出已被限幅，但积分还在涨（积分饱和） |
| **输出限幅** | PWM 直接打满 | 目标与实际差太大时输出没有上限 |

### 3.8 输出调试踩过的坑

| 坑 | 现象 | 原因 |
|---|---|---|
| `%d` 配 `float` 参数 | 打印出 `1073741824` 这类天文数字 | printf 按 4 字节整数读，读到的是浮点数的位模式 |
| `%.1f` + 勾了 MicroLIB | 数字变成 `f`，或者干脆消失 | MicroLIB 砍掉了浮点格式化 |

两个都必须显式转换：

```c
printf("%d,%d\r\n", (int)g_target, (int)g_actual);
```

> 这两种错误**都不会报错**，只会给你一堆看起来像数字的垃圾。
> 记住：`1073741824` = `0x40000000`，正好是 float `2.0` 的位模式。

### 3.9 阶跃响应的实测数据

**测试条件**：仿真对象是一阶惯性（`T = 0.1s`，`K = 3`，即 100% 输出对应 300rpm），
目标从 0 阶跃到 100，控制周期 10ms。

| 参数 | 0→90% | 超调 | 稳态 | 说明 |
|---|---|---|---|---|
| `Kp=1.0, Ki=0.5` | 89ms | 0% | 99.9996 | 偏保守，但曲线很干净 |
| `Kp=1.0, Ki=0` | 约 90ms | 0% | **74.999992** | **静差 25，与理论完全一致** |
| `Kp=2.0, Ki=0.5` | 58ms | 0% | 99.9996 | 快 35%，仍无超调 |
| `Kp=3.0, Ki=0.5` | <40ms | — | 99.9996 | 快到 20ms 采样已经测不准 |

#### 用 `Ki=0` 验证"静差"

把积分项去掉后，稳态停在 **74.999992**。理论推导：

```text
输出    out   = Kp × 误差
转速    speed = K × out = K·Kp × 误差
平衡时  speed = 目标 − 误差

  → speed = 目标 × K·Kp / (1 + K·Kp)
          = 100 × 3 / (1 + 3)
          = 75
```

**理论和实测完全吻合（75 vs 74.999992）**，这一次验证同时还说明：

- 仿真增益 `K = 3` 正确
- `Kp` 系数确实用对了
- 误差方向没写反（写成 `actual - target` 会跑飞）
- 从 PID 输出到仿真转速的整条链路是通的

结论：**P 能快速拉起响应，但永远差一截，那一截只能靠积分补。**

#### 仿真和真机的差距

以上全部来自理想仿真——没有噪声、没有死区、没有延迟。真机上：

| 差异 | 影响 |
|---|---|
| 编码器噪声 | P 大会放大噪声，PWM 跟着抖，电机"滋滋"响 |
| PWM 死区 | 小输出时电机不转，静差变大，需要更大的 I |
| 静摩擦 | 启动慢、低速爬行 |
| 采样延迟 | 相位滞后，更容易振荡 |

> **真机的响应时间通常是仿真的 1.5~3 倍，能用的最大 P 可能只有仿真的一半。**
> 仿真参数是**起点**，不是答案。它的价值在于：你已经知道一条"好的阶跃响应"该长什么样。

## 任务分工

| 任务 | 优先级 | 周期 | 职责 |
|---|---|---|---|
| `pidTask` | `AboveNormal` | 10ms | 读反馈 → 算 PID → 写输出 |
| `sinTask` | `Normal` | 10ms | 算正弦目标值 |
| `defaultTask` | `Low` | 100ms | 串口打印 |

**优先级原则：越实时的越高。** 控制最高，打印最低。

> 踩过的坑：`pidTask` 一开始用的是 `osPriorityIdle`（最低），
> 加上 `sinTask` 里漏了 `osDelay` 霸占 CPU，结果 `pidTask` 几乎跑不起来。
